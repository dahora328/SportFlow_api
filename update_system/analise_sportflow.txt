PARTE 2 — BUGS FUNCIONAIS QUE IMPEDEM CADASTROS REAIS 🐛
================================================================================

---------- BUG 1: CÓDIGO MORTO NO AthletesController@store [CRÍTICO] ----------
Arquivo: SportFlow_api/app/Http/Controllers/AthletesController.php (linhas 70-123)

O método store() tem um return na linha 91-94 que RETORNA ANTES de usar
o $request->validated(). O código das linhas 96-122 (que usa DB::transaction,
validated() e o AthletesResource) NUNCA É EXECUTADO — é código morto.

Resultado prático: Os dados validados pelo StoreAthletesRequest são IGNORADOS.
O $data que é salvo vem sem os campos validados (linha 80-81 apenas seta
owner_id e enterprise_id, mas NÃO pega os dados do formulário).

O atleta é criado com campos vazios/nulos. Isso quebrará cadastros reais.


---------- BUG 2: StoreAthletesRequest tem regras DUPLICADAS [MÉDIO] ----------
Arquivo: SportFlow_api/app/Http/Requests/StoreAthletesRequest.php (linhas 39-51)

As regras para 'email', 'mother_name', 'father_name', 'owner_id' e 'photo_path'
estão DUPLICADAS no array de rules(). As primeiras ocorrências (linhas 39-43)
são sobrescritas pelas segundas (linhas 45-50). Isso não causa erro, mas
demonstra falta de limpeza e pode confundir futuras manutenções.


---------- BUG 3: StoreEnterpriseRequest NÃO ESTÁ SENDO USADO [MÉDIO] ----------
Arquivo: SportFlow_api/app/Http/Requests/StoreEnterpriseRequest.php

O authorize() retorna FALSE (linha 15), o que significa que se alguém
tentar usar esse FormRequest, TODAS as requisições seriam bloqueadas com 403.
Porém, o EnterpriseController@store NEM USA esse FormRequest — ele recebe
um Request genérico. Ou seja, a validação de dados de empresa está ausente.
Dados inválidos podem ser salvos no banco.


---------- BUG 4: EnterpriseController@store NÃO VALIDA DADOS [ALTO] ----------
Arquivo: SportFlow_api/app/Http/Controllers/EnterpriseController.php (linha 46)

O método store() faz $data = $request->all() e passa direto para
Enterprise::create($data). NÃO há validação de campos obrigatórios
(name, document, email, etc.). Um POST vazio criaria uma empresa sem dados.

Isso é um problema tanto funcional quanto de segurança (mass assignment
é mitigado pelo $fillable, mas dados inválidos entram no banco).


---------- BUG 5: EnterpriseController@update NÃO VALIDA DADOS [ALTO] ----------
Arquivo: SportFlow_api/app/Http/Controllers/EnterpriseController.php (linha 101)

Mesmo problema do store(). O update faz $data = $request->all() sem
validação e passa para $enterprise->update($data). Não verifica se o
usuário logado tem permissão de editar AQUELA empresa.


---------- BUG 6: Rotas frontend SEM proteção de autenticação [ALTO] ----------
Arquivo: SportFlow-frontEnd/src/App.tsx

As rotas /user, /enterprise, /reports, /home, /athletes NÃO usam
ProtectedRoute. Qualquer pessoa pode acessar essas páginas sem estar logada.
Mesmo que a API retorne 401, a interface aparece e pode confundir o usuário.
Somente /admin tem proteção (SuperAdminRoute).

O componente ProtectedRoute EXISTE (em routes/ProtectedRoute.tsx e
components/ProtectedRoute/), mas NÃO ESTÁ SENDO USADO nas rotas.


---------- BUG 7: RegisterRequest NÃO é usado no AuthController [BAIXO] ----------
Arquivo: SportFlow_api/app/Http/Requests/RegisterRequest.php

O FormRequest RegisterRequest existe com validação correta, mas o
AuthController@register usa Request genérico e faz validação inline.
Não é exatamente um bug, mas duplica lógica e o FormRequest é desperdiçado.


---------- BUG 8: Log de debug no EnterpriseController@update [BAIXO] ----------
Arquivo: SportFlow_api/app/Http/Controllers/EnterpriseController.php (linhas 103-107)

Há um Log::info que imprime todos os dados da requisição no log.
Em produção, isso pode logar dados sensíveis (emails, documentos).

PARTE 3 — PROBLEMAS DE SEGURANÇA 🔒
================================================================================

---------- SEG 1: .env COMMITADO NO REPOSITÓRIO [CRÍTICO] ----------
Arquivo: SportFlow_api/.env

O arquivo .env contém:
  - APP_KEY (chave de criptografia do Laravel)
  - JWT_SECRET (chave de assinatura dos tokens JWT)
  - DB_PASSWORD (senha do banco de dados)

Se o repositório for público ou compartilhado, qualquer pessoa pode:
  - Forjar tokens JWT válidos
  - Descriptografar dados criptografados pelo Laravel
  - Acessar o banco de dados diretamente

AÇÃO: Rotacionar TODAS as chaves secretas imediatamente se este repo
já foi compartilhado. Adicionar .env ao .gitignore (já está, mas o
arquivo já foi commitado antes).


---------- SEG 2: docker-compose.yml com credenciais FRACAS [CRÍTICO] ----------
Arquivo: docker-compose.yml (linhas 35-37)

  POSTGRES_USER: user
  POSTGRES_PASSWORD: password

Essas são credenciais padrão que qualquer atacante testará primeiro.
Além disso, a porta 5432 está EXPOSTA para fora do Docker (ports: "5432:5432"),
permitindo acesso direto ao banco de qualquer lugar na rede.


---------- SEG 3: APP_DEBUG=true e APP_ENV=local [ALTO] ----------
Arquivo: SportFlow_api/.env (linhas 2-4)

Em produção, APP_DEBUG=true expõe stack traces completos, incluindo:
  - Caminhos de arquivos do servidor
  - Variáveis de ambiente
  - Queries SQL
  - Credenciais de banco

Isso dá a um atacante tudo que ele precisa para explorar o sistema.


---------- SEG 4: refresh_token e refresh_token_expires_at no $fillable [ALTO] ----------
Arquivo: SportFlow_api/app/Models/User.php (linhas 37-45)

Os campos 'refresh_token' e 'refresh_token_expires_at' estão no $fillable
do User. Isso significa que num request de criação/edição de usuário,
alguém mal-intencionado poderia enviar esses campos para manipular o
refresh token de um usuário, potencialmente sequestrando sessões.

Além disso, 'refresh_token' NÃO está no $hidden, então ele é retornado
no JSON do endpoint /user (/api/user). Qualquer pessoa autenticada
pode ver o hash do seu refresh token.


---------- SEG 5: EnterpriseController@show NÃO verifica permissão [ALTO] ----------
Arquivo: SportFlow_api/app/Http/Controllers/EnterpriseController.php (linhas 77-86)

O método show(int $id) permite que qualquer usuário autenticado veja
os dados de QUALQUER empresa, passando qualquer ID na URL.
Não há verificação de enterprise_id do usuário logado.


---------- SEG 6: EnterpriseController@update SEM verificação de dono [ALTO] ----------
Arquivo: SportFlow_api/app/Http/Controllers/EnterpriseController.php (linha 99)

Qualquer usuário autenticado pode editar QUALQUER empresa. Não há
verificação se o usuário pertence àquela empresa ou se é Super Admin.
Um gestor da Empresa A poderia editar os dados da Empresa B.


---------- SEG 7: EnterpriseController@destroy SEM verificação de dono [ALTO] ----------
Arquivo: SportFlow_api/app/Http/Controllers/EnterpriseController.php (linha 125)

Qualquer usuário autenticado pode deletar QUALQUER empresa.
Não há verificação de permissão. Um funcionário poderia deletar
a própria empresa ou qualquer outra.


---------- SEG 8: CORS permite apenas localhost [MÉDIO] ----------
Arquivo: SportFlow_api/config/cors.php e app/Http/Middleware/Cors.php

O CORS está configurado para 'http://localhost:5173'. Quando o sistema
for para produção com um domínio real, isso precisará ser atualizado.
Há DUPLICAÇÃO de configuração CORS (config/cors.php + middleware Cors.php).
A duplicação pode causar conflitos.


---------- SEG 9: Tokens armazenados no localStorage [MÉDIO] ----------
Arquivo: SportFlow-frontEnd/src/contexts/AuthContext.tsx

Access token e refresh token são armazenados no localStorage.
Isso os torna vulneráveis a ataques XSS (Cross-Site Scripting).
Se qualquer script malicioso rodar na página, ele pode roubar os tokens.

Alternativa mais segura: cookies httpOnly + secure (o backend seta
o cookie e o browser envia automaticamente).


---------- SEG 10: Sem rate limiting nas rotas de login [MÉDIO] ----------
Arquivo: SportFlow_api/routes/api.php (linha 13)

A rota /login não tem throttle/rate limiting. Um atacante pode fazer
brute-force de senhas sem limitação. O Laravel tem o middleware
'throttle' nativo que deveria ser aplicado.


---------- SEG 11: Sem validação de CNPJ/CPF no backend [BAIXO] ----------
Arquivos: StoreAthletesRequest.php, EnterpriseController.php

Os campos 'document' aceitam qualquer string. Não há validação de
formato de CPF (###.###.###-##) ou CNPJ (##.###.###/####-##), nem
validação do dígito verificador. Dados inválidos podem entrar no banco.


---------- SEG 12: Senha fraca aceita (mínimo 6 caracteres) [BAIXO] ----------
Arquivo: SportFlow_api/app/Http/Controllers/AuthController.php (linha 34)

A política de senha aceita qualquer coisa com 6+ caracteres.
Para dados reais de empresas, seria recomendável exigir:
  - Mínimo 8 caracteres
  - Pelo menos 1 letra maiúscula, 1 minúscula, 1 número


---------- SEG 13: endpoint /user expõe dados sensíveis [BAIXO] ----------
Arquivo: SportFlow_api/app/Http/Controllers/AuthController.php (linha 150)

O endpoint /me retorna auth()->user() diretamente. Isso inclui
campos como refresh_token (hash) e refresh_token_expires_at.
Deveria usar um UserResource para filtrar os campos retornados.
